# Work Experience: Presenter Overview

**For:** Teachers, mentors, or anyone opening the programme
**Format:** Slide deck with speaker notes
**Duration:** 20–30 minutes (kickoff on Day 1)
**Audience:** Students (Year 12, age 16–17) + optional parents/staff

---

## Slide 1 — Title

```
WORK EXPERIENCE
Software Engineering Programme

Two weeks. Real code. Ship something.
```

**Speaker notes:**
"Welcome — over the next two weeks you're going to build a real web application and put it on the internet. Not a tutorial project, not a school exercise — something you built, from scratch, that works. By the end of Day 10 you'll demo it to the group. Let's talk about what that looks like."

---

## Slide 2 — What this is (and isn't)

```
THIS IS NOT...                  THIS IS...

A coding course                 A software team simulation
Copying from tutorials          Designing and building your own solution
Working alone                   Working in a team with roles
Marked on correctness           Judged on shipping something real
```

**Speaker notes:**
"This isn't a lesson. There are no right answers, no mark schemes. We're simulating what it's like to work at a software company — you'll have a brief, a team, and a deadline. The goal isn't perfect code. The goal is something working that you can demo."

---

## Slide 3 — The two-week shape

```
WEEK 1: FIGURE IT OUT          WEEK 2: SHIP IT

Day 1  Set up & pick project   Day 6  Build core features
Day 2  Learn the tools         Day 7  Connect everything
Day 3  Build something rough   Day 8  Fix, polish, test
Day 4  First working version   Day 9  Write the README
Day 5  Review & replan         Day 10 Demo day
```

**Speaker notes:**
"Week 1 is messy — that's expected. You'll hit walls, get confused, ask for help. Week 2 is about turning what you have into something polished and presentable. Day 10 is fixed: everyone demos, regardless of where they are. Shipping on time with 80% of the features is better than not shipping at all."

## Slide 5 — How to pick a project

```
PICK A PROJECT THAT...

✓ At least one person in the team finds genuinely interesting
✓ Has a curriculum link to a subject you're studying
✓ Matches your team's comfort level (honest assessment)
✓ You can explain what it does in one sentence

AVOID...

✗ Picking the hardest one to impress people
✗ Picking at random without reading the brief
✗ Splitting up and each person picking separately
```

**Speaker notes:**
"You have about 20 minutes now to read through the project list and discuss as a team. Open `projects/README.md` — there's a one-paragraph summary of each. Once you've picked, open the full brief in that project's folder. The brief is detailed: it tells you what to build, who does what, and what to do on each day."

## Slide 6 — Team roles

```
EVERY PROJECT HAS 3–4 ROLES

Frontend developer     → what the user sees (HTML, CSS, React)
Backend / logic        → data, calculations, APIs
Data / visualisation   → charts, maps, numbers
DevOps / PM            → GitHub, deployment, keeps things moving

One person can cover two roles on a small team.
Roles are guides, not rigid — help each other.
```

**Speaker notes:**
"The brief for each project suggests specific roles. Read those before you divide up the work — they're based on what that project actually needs. The most important thing is that everyone knows what they're responsible for. Nothing kills a team project faster than two people building the same thing, or nobody building a critical piece."

## Slide 7 — How the day works

```
09:00  Standup (10 min, standing up)
       "What did I do yesterday?"
       "What am I doing today?"
       "Any blockers?"

09:10  Deep work block

12:30  Lunch

13:15  Afternoon work block

16:30  Commit everything to GitHub
       Write one sentence in your team log

17:00  Done
```

**Speaker notes:**
"The standup is non-negotiable. Ten minutes, everyone speaks. It surfaces blockers early and keeps the team aligned. The commit at end of day is also non-negotiable — everything goes to GitHub before you leave. If your laptop breaks tomorrow, nothing is lost. If you haven't committed it, it doesn't exist."

---

## Slide 8 — Getting unstuck

```
WHEN YOU'RE STUCK, IN ORDER:

1. Read the error message carefully (actually read it)
2. Search the error message + language name online
3. Ask an AI coding agent (e.g. Auggie) — paste the error + your code
4. Ask a teammate
5. Ask a mentor

Don't sit stuck for more than 15 minutes without doing one of these.
```

**Speaker notes:**
"Being stuck is not failure — it's the job. Professional developers spend a significant part of their day debugging. The skill is getting unstuck quickly. AI tools are genuinely useful here: paste in your error message and the relevant code and ask it to explain what's wrong. But read the explanation — don't just copy the fix without understanding it."

  javascript-tutorial.html  Variables, arrays, arrow funcs, DOM

Open any file in a browser. No install. No build.

```

**Speaker notes:**
"If anyone on the team feels rusty on Git, Python, or JavaScript, point them at the `tuts/` folder. Each tutorial is a single HTML file — no install, no build, just double-click to open in a browser. You get concepts up top, a few hands-on exercises, then a 7-question quiz with instant feedback and a running score. About 30–45 minutes per tutorial. Useful on Day 1 if setup finishes early, and any time later in the fortnight when someone hits a fundamentals wall."

```
BY DAY 10, YOUR TEAM WILL HAVE:

□ A working app that runs in a browser
□ A public GitHub repository with real commit history
□ A README explaining what it is and how to run it
□ A 5-minute live demo with talking points

## Presenter notes — running the programme

These are for the teacher or mentor running the experience, not for students.

### Before Day 1
- Clone this repo and have it open on a shared screen
- Confirm student laptops can install Node.js and Python (admin rights may be needed — check with IT in advance)
- If any students want to use the AI Study Buddy (project 09) or Calculus Explainer (project 10), you'll need an LLM API key set up ahead of time
- Optional: create a Slack or Teams channel for the group

### Day 1 checklist
- [ ] Show slides 1–11 (this deck) — 20–25 minutes
- [ ] Students read welcome guide and set up machines
- [ ] Teams form and pick projects (keep teams to 3–5)
- [ ] Each team creates a GitHub repo and invites all members
- [ ] Before leaving: everyone has committed a file (even just a README)

### Daily rhythm
- Hold the 09:00 standup yourself for the first two days so students see what it looks like, then hand it to a student to run
- Check in with each team mid-morning: are they on the right day in the brief?
- The brief's day-by-day plan is a guide, not a guarantee — some teams will be ahead, some behind. That's fine.

### Common blockers to watch for
- **Setup takes too long on Day 1** — pair students up so one helps the other
- **Team not dividing work clearly** — ask them to each say aloud what they're working on right now
- **Stuck on a concept** — suggest the AI tool first, then explain if needed
- **Scope creep** — if a team is adding features in Week 2 instead of finishing core ones, redirect them back to the brief's MVP list

### Demo day (Day 10)
- 5 minutes per team, strict
- Audience: other student teams + any guests (parents, staff)
- Ask each team: "what was the hardest problem you solved?" — gets good answers
- Celebrate shipping, not polish
